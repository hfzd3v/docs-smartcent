I’ll simulate this exactly as if you were starting your invoice SaaS knowledge base next week.

⸻

Day 1: Initial Setup

Install

npm create astro@latest

Choose:

Project: docs
Template: Empty
Install dependencies: Yes
Typescript: Strict

Install Starlight:

npx astro add starlight

Result:

docs/
├─ src/
├─ astro.config.mjs
├─ package.json
├─ public/
└─ ...

⸻

Configure Starlight

astro.config.mjs

import { defineConfig } from 'astro/config';
import starlight from '@astrojs/starlight';
export default defineConfig({
  integrations: [
    starlight({
      title: 'InvoiceApp Docs',
      social: {
        github: 'https://github.com/company/docs'
      },
      sidebar: [
        {
          label: 'Getting Started',
          items: [
            { slug: 'getting-started/overview' }
          ]
        }
      ]
    })
  ]
});

Run:

npm run dev

Open:

http://localhost:4321

You now have a documentation website.

This is why I think Starlight fits your use case so well. The workflow remains almost unchanged from day 1 to year 3:

Write Markdown
      ↓
Git Push
      ↓
Cloudflare Deploy

while Docusaurus teams often start similarly but gradually accumulate React components, plugins, theme customizations, and other maintenance overhead as the site grows. For a documentation-driven acquisition strategy, that simplicity is often a better return on engineering time.
